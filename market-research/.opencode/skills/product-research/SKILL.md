# Product Research

## Language contract

Use English for internal reasoning, workflow control, source comparison, and tool-oriented instructions. This improves consistency for technical terms without changing the research scope or evidence standard.

All user-facing communication must be in Russian: clarification questions, progress updates, limitations, final messages, and every generated Markdown deliverable. Preserve the exact Russian report headings, table labels, hypothesis evidence levels, and status explanations from `references/report-template.md`; do not translate them. Keep Russian market phrases, Yandex/Avito terminology, source names, quotations, and examples in their original form.

When this file contains an English instruction and a Russian required output label, follow the English instruction internally and render the required label in Russian. Do not expose English-only planning notes, tool traces, or intermediate reasoning to the user.

## Область применения, справочные файлы и бюджет

Этот skill ориентирован на **рынок РФ**: его источники и канал поиска по умолчанию — Яндекс MCP (`yandex-analytics`), Авито Аналитика и Яндекс Поиск. Не представляй его как международный workflow и не подменяй источники иностранными без явного решения пользователя. Для другого рынка сначала задай отдельную карту источников и правила проверки.

Открывай справочный файл, только когда выполнено его условие:

- `references/sqlite-schema.md` — до первой записи в SQLite;
- `references/mcp-preflight.md` — до вызова любого MCP-источника;
- `references/run-manifest-template.json` — до начала нового исследования;
- `references/geography-coverage.md` — до выбора регионов и первого аналитического вызова;
- `references/marketplace-category-analysis.md` — перед сбором category-метрик Авито или другой площадки;
- `references/chart-policy.md` — перед созданием любого графика;
- `references/charts-spec-template.json` — при подготовке воспроизводимых SVG-графиков;
- `references/chart-rendering-qc.md` — после генерации SVG и после сборки PDF с графиками;
- `references/pdf-delivery.md` — после финализации Markdown-отчёта и перед выдачей результата;
- `references/source-degradation.md` — когда любой источник недоступен, заблокирован или неполон;
- `references/social-channel-validation.md` — когда Stage 0 признаёт социальные сети вероятным каналом поиска, портфолио или заказа;
- `references/paid-demand-test.md` — когда пользователь явно просит подготовить или провести платный рекламный тест;
- `references/report-template.md` — до подготовки Markdown-отчёта;
- `references/extended-quality-gate.md` — после блокирующего quality gate для полного отчёта.

Бюджет по умолчанию на одно исследование: не более 12 вызовов Wordstat, 10 вызовов Авито, 10 поисковых запросов Search API (или один отложенный батч до 50 запросов) и 25 открытых публичных страниц. Для сбоя источника допустимы не более двух повторов. Превышай лимит только если в разделе «Исходные данные» записана причина, по которой дополнительные данные способны изменить решение; иначе останови расширение и укажи ограничение.

## Иерархия правил

При конфликте следуй более высокому уровню. Не используй числовой score уверенности: выражай уверенность уровнем подтверждения, фактами и пробелами данных.

- **BLOCKER:** не выдай `GO`, `TEST` или `NO-GO`, а остановись либо поставь `HOLD`, если придумана или не прослеживается ключевая метрика, оба рыночных MCP не дали данных, или вывод превышает разрешённый в матрице деградации уровень. При `channel_mismatch` переключись на B2B-ветку либо выдай `Channel-fit brief`.
- **CRITICAL:** продолжай только с явным ограничением и статусом, который ему соответствует, если нет триангуляции источников, отсутствует обязательный «Журнал поисковых запросов», либо доступна лишь широкая категория вместо данных по продукту.
- **REQUIRED:** выполни правило или укажи конкретную причину пропуска: запись в SQLite, «История исследования», период/регион/уровень каждой метрики, «Исходные данные» и предвыдачная проверка структуры отчёта.
- **SOFT:** улучши полноту, но не подменяй факты: размер систематической выборки, число регионов, дополнительные отзывы и оформление таблиц.

## Назначение

Используй этот skill для исследования рынка физического товара или продуктовой идеи. Исходное название товара — это гипотеза, а не окончательный поисковый запрос.

Цель: понять, как покупатели называют товар, есть ли измеримый спрос, насколько велико предложение, где возможен дефицит, как меняются показатели во времени и какие продуктовые гипотезы подтверждаются данными.

Используй минимум два независимых источника:

1. **Яндекс MCP (`yandex-analytics`)** — внешний поисковый интерес: Wordstat (частотность, динамика, география) и Search API (поисковая выдача: URL + сниппет).
2. **Авито Аналитика MCP** — спрос и предложение внутри торговой площадки.

Если доступен **Playwright MCP**, используй его как третий слой — web validation: для проверки реальных офферов, ценовых диапазонов, позиционирования, каналов покупки и отзывов на публично доступных страницах. Playwright — это браузерный инструмент, а не самостоятельный источник рыночных цифр.

Показатели этих источников не взаимозаменяемы. Не подменяй данные общими знаниями, не придумывай отсутствующие цифры и всегда отделяй факт от интерпретации.

## SQLite MCP — обязательное накопление истории

Если SQLite MCP виден среди доступных инструментов и пользователь не запретил сохранение результатов, используй его обязательно для накопления **измеримых наблюдений** между исследованиями. Яндекс MCP и Авито Аналитика MCP остаются источниками рынка; SQLite хранит результаты их вызовов и не заменяет их.

SQLite нужен, чтобы сравнивать рынок во времени: например, спрос на товар сегодня с показателями предыдущего исследования. Он не является источником рыночных данных и не заменяет Яндекс или Авито.

### Безопасность и область доступа

- Работай только с базой, уже подключённой SQLite MCP: `sqlite.db` в корне текущего проекта.
- Не обращайся к произвольным SQLite-файлам компьютера.
- Не сохраняй токены, cookies, полные секретные ответы MCP или персональные данные.
- Не создавай альтернативную БД по другому пути без явного изменения конфигурации MCP.
- Если SQLite MCP недоступен или запись не удалась, выполни исследование без истории, но обязательно укажи это в разделе «История исследования» и не делай выводов о динамике на основе отсутствующих данных.

### Обязательная последовательность

До вызова источников:

1. Проверь доступ SQLite MCP к `sqlite.db`.
2. Прочитай `references/sqlite-schema.md` и выполни его DDL без изменения имён таблиц или полей.
3. Создай запись текущего запуска в `research_runs` и используй её `research_run_id` во всех сохранённых наблюдениях.
4. Найди сопоставимые предыдущие наблюдения до формулирования вывода о динамике.

После каждого содержательного этапа сохраняй полученные измеримые данные. После Stage 3 сохраняй снимки узлов категорий в `market_category_snapshots`; после Stage 3.5 сохраняй систематическую выборку конкурентов в `competitor_samples`. Не откладывай все записи до конца исследования.

### Как использовать историю

До анализа сравнивай только записи с теми же запросом или кластером, источником, регионом, метрикой и периодом. Если сопоставимость нарушена, не вычисляй тренд.

Если найдены сопоставимые прошлые значения, добавь в «История исследования» компактный diff: предыдущий `research_run_id`, число новых наблюдений текущего запуска, число сопоставимых прошлых наблюдений и изменение каждой использованной метрики в абсолютном и процентном виде. Не вычисляй процент при нулевой или отсутствующей базе; напиши `не рассчитывается`. Исторические строки не удаляй и не называй устаревшими без отдельного правила хранения.

Всегда укажи в разделе «История исследования» путь БД, статус доступа, текущий `research_run_id` и ограничение сопоставимости.

## Вход

Пользователь передаёт название товара, продуктовую идею или задачу покупателя. При необходимости уточни:

- регион и период анализа;
- целевой сегмент (B2C, профессионалы, малый бизнес);
- является ли товар новым, б/у, услугой или комплектующим;
- ограничения по цене, производству или партии.

Если уточнений нет, исследуй Россию, текущий доступный период и отдельно укажи эти допущения.

### Geography gate

До preflight прочитай `references/geography-coverage.md` и зафиксируй в разделе «Цель и условия исследования» и паспорте запуска: запрошенную географию, фактическое покрытие каждого источника и допустимый тип вывода. Не выбирай город из текущей сессии Авито как «якорный», «локальный» или «типичный»: состояние браузера — технический контекст, а не решение пользователя о рынке.

Для запроса «Россия» выбери один режим:

- `national_sources_only` — по умолчанию, когда нужна общероссийская карта спроса и предложения. Wordstat и публичные витрины имеют покрытие РФ; городские метрики Авито не запрашивай и не используй как подтверждение по России.
- `national_with_city_sample` — только когда пользователь явно просит сравнить города или согласовал городскую выборку. До вызовов запиши список городов, критерий выбора и бюджет. Даже пять и более городов — сравнительная, а не репрезентативная выборка: вывод только «среди проверенных городов».
- `target_city` — только когда пользователь назвал город либо отдельно одобрил локальный тест. Не расширяй такой вывод до РФ.

Если для решения нужна именно национальная метрика Авито, а MCP возвращает только города, прямо укажи, что метрика недоступна. Не заменяй её Москвой, Сургутом или средним нескольких городов.

## Паспорт запуска и preflight источников

До первого запроса создай рядом с будущим отчётом `research/<product-slug>/run-<YYYY-MM-DD>-<run-id>.json` по `references/run-manifest-template.json`. Заполни фактические доступные инструменты, регион, лимиты, время запуска и состояние источников. Не записывай в паспорт токены, cookies или ответы целиком.

Затем прочитай `references/mcp-preflight.md` и выполни preflight. В частности:

- для `yandex-analytics` проверь доступность Wordstat и Search API; Search API без отдельного ключа или роли — это недоступный web-discovery, а не причина подменять его браузерной выдачей;
- для `avito-analytics` сначала вызови `avito_session_open`, затем `avito_session_status`; только `authorized: true` разрешает `avito_market` и `avito_wordstat`;
- только для `national_with_city_sample` или `target_city` получи ID каждого согласованного города Авито через `avito_location_search` с `exact: true`. Никогда не подставляй ID региона Яндекса в вызов Авито, не храни ID как универсальный и не подменяй согласованный список текущей локацией профиля;
- зафиксируй `requests_in_session`, `blocked_until` и допустимый остаток бюджета в паспорте. Вызовы управления сессией и поиск локации не входят в аналитический бюджет, но должны быть отражены;
- если Авито возвращает 403, 429, капчу или статус с `blocked_until`, не повторяй аналитический вызов: сервер уже ставит безопасную паузу. Запиши ограничение и сразу используй матрицу деградации.

## Цель и условия исследования

До вызова источников сформулируй раздел «Цель и условия исследования» не длиннее 8–12 строк. Он содержит:

- **Решение:** что пользователь должен выбрать по итогам исследования.
- **Объект проверки:** товар, услуга или конкретный сценарий использования.
- **Ограничения:** бюджет теста, срок, производственные возможности, допустимый канал и регион.
- **Критерий успеха:** какое наблюдение позволяет перейти к следующей проверке.
- **Стоп-критерий:** какое наблюдение прекращает или откладывает гипотезу.
- **География:** запрошенный охват, режим (`national_sources_only`, `national_with_city_sample` или `target_city`) и граница допустимого вывода.

Если пользователь не указал часть параметров, не выдумывай их как факты. Выбери осторожные рабочие допущения, явно пометь их и используй только для планирования исследования. Запроси уточнение, если отсутствующий параметр способен материально изменить объект исследования.

В конце полного отчёта и `Channel-fit brief` обязательно укажи итоговый статус:

- `GO` — достаточно данных, чтобы переходить к согласованному следующему шагу;
- `TEST` — есть проверяемая гипотеза, но нужны предзаказы, интервью или пилот;
- `HOLD` — данных недостаточно либо есть существенное ограничение;
- `NO-GO` — доступные данные противоречат гипотезе в заданных ограничениях.

`GO` не означает разрешение на массовое производство или инвестиции, если не проверены экономика, требования соответствия и реальная покупка.

## Общие правила

- Сначала исследуй язык рынка, затем измеряй спрос.
- Не делай общероссийский вывод по одному запросу, одному городу или одному источнику. Метрика города Авито сохраняет метку города даже если остальные источники имеют покрытие РФ.
- Не складывай несопоставимые метрики Wordstat и Авито.
- Записывай дату, источник, запрос, регион и период для каждой использованной метрики.
- Если MCP не дал показатель, прямо обозначь его как недоступный.
- Если источники противоречат друг другу, не усредняй их: опиши противоречие и предложи его проверку.
- Если источник недоступен, заблокирован или даёт неполные данные, до вывода прочитай `references/source-degradation.md` и соблюдай допустимый для комбинации источников уровень вывода.

### Уровень данных и границы вывода

Для каждой метрики укажи её уровень:

- `query` — конкретный поисковый запрос;
- `cluster` — группа поисковых запросов;
- `category` — широкая категория площадки;
- `listing` — конкретные релевантные объявления;
- `region` — географический срез.

Не переноси вывод с широкого уровня на узкий. Например, показатели категории «Баня» нельзя называть показателями «срубов бань из бревна», пока категория не отфильтрована по конструкции или не подтверждена отдельным анализом релевантных объявлений.

Если сопоставлены не все регионы, пиши «лучший среди проверенных регионов», а не «лучший в России». Городская выборка Авито не является общероссийской и не используется для общероссийских суммы, средней, конверсии или статуса спроса. Для рекомендации региона нужны: поисковый интерес, сопоставимый отклик и предложение по конкретному товару, а также проверка цен, логистики и экономики.

## Workflow

### Stage 0 — Channel-fit gate

До глубокого анализа проверь, подходит ли Wordstat + Авито для данного способа покупки. После первичной семантики и нескольких проверок Авито классифицируй путь покупки:

- `B2C search / marketplace` — покупатель ищет готовый товар и сравнивает предложения;
- `B2B direct / service` — покупатель приходит через сервисника, рекомендацию, интегратора, тендер или прямые продажи;
- `regulated procurement` — решение покупается из-за регламента, проверки или закупочной процедуры;
- `mixed` — сочетаются несколько путей.

Установи статус `channel_mismatch` и не продолжай глубокую оценку спроса, географии и продуктовых возможностей через Wordstat + Авито, если одновременно выполняются условия:

- проблема не формулируется покупателем как поисковый запрос товара или услуги;
- Авито не показывает релевантного query- или listing-уровня, а доступна только слишком широкая категория;
- предполагаемый покупатель обычно приобретает решение через сервисную компанию, поставщика оборудования, интегратора, тендер или личный контакт.

`channel_mismatch` означает только, что текущие источники не видят путь покупки. Он **не означает отсутствия рынка**.

### Проверка социальных каналов

В Stage 0 отдельно укажи `social_channel_relevant: yes` или `no` и краткую причину. Установи `yes`, если для локального B2C, заказного изделия, услуги мастера, мероприятия или персонализированного товара публичная страница в социальной сети вероятно служит витриной, портфолио или способом заказа. Для промышленного B2B, регулируемых закупок и иных сценариев без такого признака не трать веб-бюджет на социальные сети.

При `social_channel_relevant: yes` до Stage 3.5 прочитай `references/social-channel-validation.md`. Социальные сети дополняют Wordstat, Авито и web validation; они не являются самостоятельным источником рыночного спроса или продаж.

### B2B direct / service / regulated procurement branch

Если путь покупки классифицирован как `B2B direct / service` или `regulated procurement`, переключи исследование на эту ветку. Не пытайся заменить первичные B2B-данные частотностью Wordstat или широкой категорией Авито.

Через Playwright MCP, если он доступен, собери 5–10 публичных источников по релевантному пути покупки:

- сервисные компании и монтажники;
- интеграторы и поставщики оборудования;
- сайты производителей и отраслевые каталоги;
- публичные завершённые закупки, если покупатель может быть государственным или муниципальным;
- профессиональные сообщества и вакансии — только как вторичный контекст.

Составь карту покупки:

```text
проблема → инициатор → принимающий решение → канал покупки → исполнитель/партнёр → внедрение → поддержка
```

Подготовь `B2B discovery brief` со следующими разделами:

1. проверенные сигналы и пробелы данных;
2. предполагаемые роли: пользователь, инициатор, плательщик, сервисный партнёр;
3. ценность для клиента и отдельно для возможного партнёра;
4. список 5–10 кандидатов для контакта без публикации персональных данных;
5. 5–7 вопросов для интервью;
6. минимальный пилот с одним партнёром или 1–3 клиентами;
7. статус `TEST`, `HOLD` или `NO-GO`.

Не делай вывод о размере B2B-рынка, готовности платить или ценовой конкуренции, пока это не подтверждено интервью, завершёнными закупками или реальными коммерческими предложениями.

В этом случае подготовь короткий Markdown-отчёт `Channel-fit brief` вместо полного рыночного отчёта:

1. какие сигналы проверены и что именно не видно в текущих источниках;
2. предполагаемый путь покупки;
3. что остаётся гипотезой;
4. план первичной проверки: интервью с покупателями, сервисными компаниями, интеграторами или поставщиками; анализ завершённых закупок для B2G; пилот с партнёром;
5. 5–7 конкретных вопросов для интервью.

Не компенсируй отсутствие данных вымышленными размерами рынка, ценами, потерями клиентов или предположениями о конкуренции.

### Stage 1 — Semantic discovery

Используй Яндекс MCP (`yandex-analytics`, инструменты Wordstat) для расширения семантики. Найди:

- основные названия;
- синонимы и варианты написания;
- профессиональные и бытовые названия;
- запросы по задаче, которую решает товар;
- поводы покупки: событие, срочность, получатель или ограничение, если они меняют оффер;
- модификации, размеры, материалы и ценовые сегменты;
- смежные товары и нерелевантные омонимы.

Для каждого запроса укажи намерение: `commercial`, `informational`, `professional`, `adjacent` или `irrelevant`. Сформируй 10–30 релевантных запросов, сгруппированных в кластеры. Если товар узкий, допускается меньше запросов — объясни почему.

Для локальных B2C, заказных товаров и услуг укажи для каждой коммерческой фразы также `occasion`: например, день рождения, детский праздник, свадьба, корпоратив, без повода, срочно, диетическое ограничение или `не определён`. Не выводи повод только из названия товара без подтверждения семантикой или публичными предложениями.

Не суммируй частотности пересекающихся запросов, например «сруб бани», «купить сруб бани» и «сруб бани цена», как размер спроса: они могут описывать один и тот же поисковый интерес. Используй такие фразы для анализа намерения и структуры семантики. Точную суммарную частотность указывай только при явном методе дедупликации; иначе помечай её как недоступную.

Пример для плотницкой черты: `плотницкая черта`, `черта для сруба`, `скрайбер для бревна`, `разметка бревен`, `разметочный циркуль`. Не считай все примеры одинаково релевантными без проверки.

### Stage 2 — Search demand

Для каждого коммерческого кластера через Яндекс MCP (инструмент Wordstat) собери доступные показатели:

- частотность;
- динамику;
- сезонность;
- географию.

Если данные позволяют, сравни сезонность и географию не только по товару, но и по поводам покупки. Для `national_with_city_sample` покажи отдельную таблицу городов, критерий их выбора и метку «среди проверенных городов»; не агрегируй города в показатель России.

Отдели товарные запросы от информационных. Укажи, какие данные получены непосредственно из MCP, а какие отсутствуют.

### Stage 3 — Marketplace validation

Для коммерческих запросов и кластеров используй `avito_wordstat` и `avito_market` только после успешного preflight. В каждом успешном ответе сохрани поле `archived` как `evidence_ref` в SQLite и в разделе «Исходные данные»: это путь к исходному JSON, а не замена описания метрики. Перед category-вызовами прочитай `references/marketplace-category-analysis.md`: сначала зафиксируй целевую категорию и собери только её ветку из 2–4 узлов для каждого согласованного города, а не нерелевантную сводку «все категории». Сохрани узел, ID, родителя, глубину, показатели и период в `market_category_snapshots`. Собери доступные показатели:

- спрос;
- число предложений;
- контакты или конверсию, если доступны;
- динамику;
- сезонность;
- регионы;
- цену, если доступна.

Не путай данные Аналитики спроса, публичную выдачу и статистику собственного аккаунта: это разные источники и разные метрики.

Контакты на объявление и просмотры на объявление называй показателями **интенсивности отклика**, а не прямым дефицитом предложения. Вывод «дефицит предложения» допустим только при наличии сопоставимых данных по конкретному продукту: релевантные объявления, контакты, цена и состав/качество предложения.

### Stage 3.5 — Web validation (Search API + Playwright MCP)

Discovery-слой web validation выполняется через **Search API** MCP `yandex-analytics` (официальный серверный API Яндекса, без капчи и браузера) — это поиск по умолчанию для рынка РФ. Playwright MCP используется только для **открытия конкретных публичных страниц**, найденных через Search API или предоставленных пользователем: чтение карточек продавцов, товаров, каталогов и социальных сетей. Не используй Playwright для листания поисковой выдачи в браузере. Не используй Google как основной поисковый канал. Не пытайся механически собрать 50–100 страниц: сначала собери 10–25 релевантных страниц из нескольких независимых типов источников, затем расширяй выборку только если она меняет вывод.

Сначала перенеси в веб-проверку язык рынка из Stage 1–2. Выбери 3–8 приоритетных фраз с намерением `commercial` и, если путь покупки профессиональный, релевантные `professional`-фразы. Приоритет: точные фразы с измеримым спросом, фразы с ясной модификацией и фразы, по которым Авито показал отдельный сигнал. Выполни поиск по этим формулировкам без замены их общими словами.

Поисковые запросы делятся на два типа:

- **Синхронно (`yandex_search_sync`)** — 3–8 приоритетных фраз, когда результаты нужны сразу (чтобы выбрать страницы для открытия). На таком объёме это копейки.
- **Отложенный батч (`yandex_search_deferred_submit`)** — массовое расширение: все модификации, все регионы, `site:`-запросы (в т.ч. `site:avito.ru`). Результаты готовы минимум через 5 минут и хранятся 12 часов. Отправь батч в начале Stage 3.5, затем выполняй другие этапы (Wordstat, Авито, открытие страниц по приоритетным фразам) и собери результаты `yandex_search_deferred_get` не раньше чем через 5 минут. **Агент обязан явно сообщить пользователю, что результаты отложенного поиска будут собраны после ожидания не менее 5 минут.**

Затем расширь проверку дополнительными запросами по четырём направлениям:

- товар и модификации: `<товар> купить`, `<товар> цена`, `<товар> на заказ`;
- сценарий и боль: `<задача клиента>`, `<проблема> решение`;
- конкуренты и каналы: `<товар> производитель`, `<товар> мастерская`, `<товар> отзывы`;
- площадки: `site:market.yandex.ru <товар>`, `site:avito.ru <товар>`, а также запросы для релевантных маркетплейсов и каталогов.

Шаблонные запросы дополняют коммерческую семантику, а не заменяют её. Не подменяй, например, точную фразу `ночник ссср` общим запросом `ретро-ночник купить`, пока не проверена выдача по исходной фразе.

Регионы в Search API задаются ID Яндекса: 213 — Москва, 2 — Санкт-Петербург, 973 — Сургут; полный список и ID бери из инструмента `regions_tree` (Wordstat) или Yandex-справочника регионов. Ограничение `site:avito.ru` сужает поиск по домену, но URL объявлений Авито привязаны к городу по IP пользователя: при поиске по конкретному городу открывай страницу Авито напрямую с городом в пути (`avito.ru/surgut/...`) через Playwright, а не полагайся на город в URL из выдачи Search API.

Если `social_channel_relevant: yes`, после проверки точных коммерческих фраз выполни 2–3 целевых Яндекс-запроса по социальным каналам в рамках общего лимита: `site:vk.com <товар или точная фраза> <город>`, `site:t.me <товар или точная фраза> <город>` и, при наличии в релевантной выдаче или в запросе пользователя, другой публично индексируемый домен. На социальные страницы используй 5–10 уникальных страниц внутри общего лимита 25, а не сверх него.

Если Stage 0 показывает локальный B2C, заказной товар или услугу, в той же web validation проверь публичные карточки Яндекс Карт, каталоги услуг и классифайды. Для каждого сопоставимого продавца фиксируй город или район, ассортимент, цену или минимальный заказ, сроки, доставку, способ заказа и повторяющиеся темы отзывов. Рейтинг и число отзывов характеризуют публичную витрину, но не являются размером рынка или объёмом продаж.

Сохрани в разделе «Исходные данные» журнал поисковых запросов с датой выполнения:

| Фраза Wordstat | Кластер | Намерение | Запрос (Search API) | Роль | Результат / решение |
|---|---|---|---|---|---|

В поле «Роль» укажи `точная коммерческая фраза`, `профессиональная фраза` или `расширение`, а для отложенных запросов — `отложенный батч`. Для каждой приоритетной фразы поясни, была ли она выполнена дословно, адаптирована для поиска или исключена и почему. Прямой переход по заранее известному URL допустим, но не заменяет поиск новых источников через Search API.

При проверке социальных каналов добавь в раздел «Исходные данные» таблицу «Журнал проверки социальных площадок»: исходная коммерческая фраза, запрос (Search API), платформа, открытый URL, результат либо причина исключения. Для публичных страниц используй типы источника `social_storefront` или `social_post` и сохраняй релевантные сопоставимые предложения в `competitor_samples` без изменения схемы SQLite.

### Лимит просмотра выдачи

Для каждого поискового запроса (Search API) открой через Playwright до **пяти** релевантных органических страниц. Не учитывай в этом лимите страницу самой выдачи, рекламные блоки, дубли, страницы одного и того же продавца без новых данных и недоступные страницы.

Расширь просмотр до **восьми** органических страниц по одному запросу только если:

- первые пять не содержат нужного типа источника;
- источники противоречат друг другу и требуется проверка;
- нужно набрать систематическую выборку сопоставимых конкурентов.

Сначала выбирай разные типы источников и независимых продавцов, а не первые несколько карточек одной витрины. Общий бюджет — 10–25 уникальных релевантных страниц на всё исследование; не увеличивай его без причины, меняющей вывод.

Ищи через Search API и открывай публичные страницы через Playwright:

- карточки товаров и категории маркетплейсов;
- сайты производителей, мастерских, интеграторов и сервисных компаний;
- каталоги и страницы услуг;
- обзоры, отзывы, тематические форумы и публикации покупателей;
- для B2G — публичные завершённые закупки, если этот канал релевантен.

Проверь:

- какие варианты товара или услуги фактически предлагают;
- наблюдаемые цены и ценовые диапазоны;
- материалы, комплектацию, сроки, доставку и гарантийные условия;
- повторяющиеся обещания продавцов и точки отличия;
- повторяющиеся жалобы, вопросы и барьеры покупки;
- где покупатель реально совершает покупку: маркетплейс, сайт производителя, сервисник, интегратор, тендер или личная рекомендация.

Для каждого использованного веб-факта сохрани: URL, дату доступа, тип источника, краткое содержание и уровень данных (`listing`, `seller`, `review`, `article`, `directory`, `procurement`, `social_storefront`, `social_post`). Для страницы социальной сети также сохрани платформу, город или географическое покрытие, товар/услугу, наблюдаемую цену, способ заказа, условия и дату последней публичной активности, если они видны. Цитируй страницу, а не только фрагмент поисковой выдачи.

Для релевантной публичной социальной витрины можешь разобрать до 5–10 последних доступных публикаций одного продавца: поводы покупки, офферы, цены, сроки, персонализацию, формат портфолио и способ заказа. Видимые реакции, комментарии и частоту публикаций фиксируй только как `content_context` для выбора оффера или креатива; не вычисляй из них спрос, продажи, конверсию или размер аудитории.

Не используй:

- число результатов поисковой выдачи как размер рынка;
- сниппет поисковой выдачи (Search API или браузерной) как доказательство факта без открытия исходной страницы;
- рекламные заявления продавца как подтверждённый факт;
- цены единичных карточек как среднюю рыночную цену;
- отзывы как статистически репрезентативный опрос;
- число подписчиков, лайки, просмотры, комментарии или частоту публикаций социальной страницы как доказательство спроса, продаж или размера рынка;
- данные, требующие входа в чужой аккаунт, обхода ограничений, CAPTCHA, антибот-защиты или платного доступа без явного разрешения.

Если сайт недоступен, заблокирован, закрыт или требует авторизации, не обходи защиту. Зафиксируй пробел в данных и перейди к другому публичному источнику. Недоступность ВК, Telegram или другой сети не означает, что этот канал не используется.

### Антибот-защита Авито и площадок

При открытии публичных страниц Авито (поиск объявлений, карточки) через Playwright площадка может вернуть страницу «Доступ ограничен: проблема с IP» или капчу. Это блокировка автоматизированного браузера или rate-limit по IP, а не отсутствие объявлений.

- Не выдавай блок-страницу за результат поиска и не подменяй пропущенные объявления сниппетами поисковой выдачи: сниппет Яндекса — это не объявление и не данные о спросе.
- Сделай паузу 30–60 секунд и повтори запрос; допустимо не более двух повторов.
- Если блок повторяется, зафиксируй его в разделе «Исходные данные» как ограничение (страница блокировки, её текст, дата), укажи строку матрицы деградации и перейди к другому публичному источнику или к данным Авито Аналитики.
- Не обходи защиту: не меняй прокси, фингерпринт или автоматизацию ради обхода и не решай капчу автоматически.
- Сообщи пользователю, как снять блок легально: постоянный профиль браузера (Playwright MCP без `--isolated`), однократное ручное решение капчи, пауза до «остывания» IP и снижение частоты запросов.

Капча поисковых систем больше не должна быть проблемой discovery-слоя: поиск выполняется через серверный Search API (`yandex_search_sync` / `yandex_search_deferred_submit`), где капчи и фингерпринта нет. Браузер (Playwright) нужен только для открытия конкретных публичных страниц, а не для листания выдачи.

Если Search API недоступен или заблокирован — следуй матрице деградации (`references/source-degradation.md`): не переключайся на Google как замену Яндексу, фиксируй блокировку и укажи discovery-слой неполным. Если всё же приходится открывать страницы Яндекса через Playwright (предоставленные пользователем URL), действуют правила выше: пауза 30–60 секунд, не более двух повторов, при постоянном профиле браузера — однократное ручное решение SmartCaptcha, снижение плотности запросов.

### Systematic competitor sample

Для каждого приоритетного B2C-сегмента собери систематическую выборку из 10–20 релевантных публичных предложений, если источники доступны. Для B2B-ветки собери 5–10 сопоставимых поставщиков или интеграторов.

Для каждой строки выборки зафиксируй:

| Поле | Что записать |
|---|---|
| Источник | URL и тип страницы |
| Продавец / поставщик | название организации или витрины, если опубликовано |
| Объект | точный тип товара или услуги |
| Повод покупки | событие или сценарий из предложения, либо «не указан» |
| Цена | наблюдаемая цена или «по запросу» |
| Комплектация | материалы, функции, персонализация, монтаж или поддержка |
| Условия | срок, доставка, гарантия, предоплата, если указаны |
| Канал заказа | площадка, соцсеть, карта/сайт, телефон или «не указан» |
| Отличие | основной оффер или позиционирование |
| Дата доступа | дата проверки страницы |

В выборку включай только сопоставимые предложения. Не смешивай винтаж, массовый импорт, ручную работу, услуги и премиальные изделия в одной ценовой статистике.

По каждой однородной подгруппе покажи число наблюдений, минимум, медиану и максимум цены. Если выборка меньше пяти предложений или цены несопоставимы, не рассчитывай сводные показатели и прямо укажи ограничение.

Не называй выборку полным рынком и не делай вывод «конкуренция слабая» только потому, что несколько страниц не нашлись.

### Stage 4 — Cross-analysis

Составь сравнительную таблицу:

| Повод покупки | Кластер | Запросы | Wordstat | Спрос Авито | Предложение Авито | Динамика | Регионы | Интерпретация |
|---|---|---:|---:|---:|---|---|---|

Ищи сигналы:

- высокий или растущий интерес при сравнительно низком предложении;
- рост спроса быстрее роста предложения;
- высокий внешний интерес, но слабый торговый спрос — возможная информационная тема;
- слабый Wordstat, но высокий спрос Авито — возможная профессиональная ниша;
- регионы с хорошим отношением спроса к предложению;
- спрос на конкретную модификацию товара.
- различия канала заказа, цены или ожиданий между поводами покупки.

При наличии сопоставимых значений можешь вычислить сравнительный индекс `контакты / релевантные объявления` или `просмотры / релевантные объявления`. Называй его «интенсивность отклика», указывай уровень данных и не называй его объективной ёмкостью рынка или доказанным дефицитом.

### Stage 4.5 — Evidence charts

Если график делает сравнение понятнее таблицы, до его создания прочитай `references/chart-policy.md`. Построй до пяти SVG-графиков на полный отчёт, не более одного на аналитический вопрос: динамика и сезонность, структура непересекающихся кластеров, география, предложение и отклик площадки, диапазон цен. Не добавляй графики ради оформления.

Перед генерацией сохрани `research/<product-slug>/charts-spec.json` по `references/charts-spec-template.json`: для каждого графика укажи источник, регион, период, уровень данных и `evidence_ref`. Затем запусти `scripts/generate-charts.mjs` и сохрани результат в `research/<product-slug>/charts/`. При двух и более сопоставимых category-строках добавь `market_profile` с раздельными панелями предложения, просмотров на объявление и контактов на объявление. Не рисуй Wordstat и Авито на общей шкале, не строй цену при менее пяти сопоставимых предложениях и не используй сниппеты, отзывы или реакции как числовую серию.

После генерации и после сборки PDF прочитай `references/chart-rendering-qc.md`. Каждый график должен быть проверен на соответствующей PNG-странице PDF: ни подпись, ни шкала, ни легенда не выходят за левую или правую границу; подписи не перекрывают данные; Markdown-таблицы рядом с графиками остались таблицами. При дефекте исправь `charts-spec.json`, Markdown или генератор, пересобери SVG и PDF; не выдавай PDF с обрезанным текстом.

В отчёте добавь только фактически созданные графики с относительными ссылками. Если применимый график не построен из-за недостатка или несопоставимости данных, оставь раздел «Графики» и укажи причину.

### Stage 5 — Product opportunities

Сформулируй от трёх до пяти гипотез в формате:

1. **Гипотеза.** Какой товар, версия или сегмент, для какого повода покупки и канала заказа.
2. **Уровень подтверждения.** Один из: `подтверждено данными`, `сильный сигнал, требует проверки`, `гипотеза`, `не подтверждено из доступных данных`.
3. **Подтверждающие сигналы.** Только полученные данные, с уровнем данных `query` / `category` / `listing`.
4. **Неопределённости.** Чего данных не хватает.
5. **Недорогая проверка.** Например: ограниченная партия, одно релевантное объявление, последовательный тест оффера или интервью с профессиональными покупателями.

Не утверждай, что ниша прибыльна, если не известны себестоимость, маржа, логистика и реальная конверсия. Не называй рынок зрелым, перенасыщенным или нормированным продуктом без критериев, подтверждающих эти характеристики.

### Бриф теста платного спроса

Подготавливай этот бриф только когда пользователь явно просит рекламный тест, указывает допустимый бюджет либо отдельно разрешает его планирование. Сам skill не создаёт кабинеты, кампании, пиксели, ссылки и не расходует деньги.

Бриф содержит: один оффер, сегмент или повод покупки, канал, креативную гипотезу, уникальную UTM-метку или промокод, способ обязательного вопроса «откуда узнали», целевую страницу или способ заявки и цепочку `источник → переход → заявка → оплаченный заказ → выручка`. Если пользователь предоставил себестоимость, добавь маржинальный доход с заказа. Планируй измерение стоимости перехода, стоимости квалифицированной заявки, конверсии заявки в оплаченный заказ и среднего чека; не задавай универсальные пороги успеха.

Если пользователь владеет сайтом и отдельно просит технический план VK Рекламы, в брифе можно рекомендовать пиксель и события просмотра каталога, открытия формы и отправки заявки. Не настраивай их в рамках исследования.

### Правила теста на площадке

Не размещай несколько почти одинаковых объявлений одновременно только для сравнения цен: это может нарушать правила площадки, попасть под модерацию как дубль и исказить результат.

Тестируй один фактор за раз — цену, комплектацию, размер, оффер или регион — при неизменных остальных условиях. Фиксируй:

- просмотры;
- контакты на 100 просмотров;
- долю квалифицированных обращений;
- договорённости о расчёте, замере или договоре;
- стоимость квалифицированного контакта, если использовалось продвижение.

Не устанавливай универсальный порог успеха без исходной базы сравнения. Сначала зафиксируй локальный baseline для сопоставимых объявлений, затем определи критерий продолжения теста.

## Формат результата

Перед написанием отчёта прочитай `references/report-template.md`. Сохрани его порядок разделов, включая «Исходные данные» с «Журналом поисковых запросов» и обязательную «Историю исследования». Числа в основных таблицах должны совпадать с «Исходными данными»; при расхождении исправь источник расхождения или пометь показатель непроверенным. Не публикуй секреты, токены и cookies.

Перед сохранением проверь наличие заголовков: `## 1. Цель и условия исследования`, `## 2. Допущения и ограничения`, `## 3. Язык рынка и семантика`, `## 8. Сопоставление сигналов`, `## 9.1 Графики`, `## 10. Гипотезы`, `## 11. Следующий тест`, `## 12. Статус`, `## Исходные данные`, `## История исследования`, `## PDF-версия`. Для недоступного источника оставь заголовок и кратко укажи причину вместо удаления раздела.

## Markdown deliverable

Всегда сохраняй результат исследования как Markdown-файл в рабочем проекте:

```text
research/<product-slug>/report-<YYYY-MM-DD>.md
```

Где `<product-slug>` — короткое имя исследуемого товара или проблемы латиницей через дефис. Если файл с такой датой уже существует, не перезаписывай его: добавь к имени `-<research_run_id>`.

Полный отчёт должен содержать все разделы из «Формат результата», включая «Исходные данные» и обязательную «Историю исследования». При `channel_mismatch` сохрани `Channel-fit brief` по тому же правилу именования.

Для иерархии используй Markdown-списки: каждый вложенный уровень отступай ровно на 4 пробела. Не имитируй подуровни ручными тире или HTML. Перед PDF-сборкой исправь каждый `WARN nested list`, чтобы дочерние пункты остались отдельным уровнем и в HTML, и в PDF.

В «Исходные данные» добавь ссылки `evidence_ref` на исходные ответы MCP и укажи путь созданного паспорта запуска. Не записывай в Markdown или паспорт токены, cookies, персональные данные или полные секретные ответы MCP. В финальном сообщении укажи пути отчёта и паспорта. Если рабочая среда не разрешает запись, верни готовое Markdown-содержимое и прямо укажи причину, по которой файл не создан.

## PDF deliverable

После финализации Markdown-отчёта прочитай `references/pdf-delivery.md` и собери PDF через skill `md2pdf`. Markdown остаётся единственным редактируемым первоисточником; не вноси правки только в HTML или PDF. Сохрани рядом с отчётом одноимённые `report-<YYYY-MM-DD>.html` и `report-<YYYY-MM-DD>.pdf`; каталог `pdf-check/` используй для проверочных PNG и `_check.txt`.

Перед выдачей полного отчёта PDF обязателен: исправь предупреждения разметки таблиц, проверь ключевые фразы в `_check.txt`, ненулевой размер PDF и PNG-страниц. При наличии SVG-графиков дополнительно проверь, что в PDF есть векторные drawings. В раздел «PDF-версия» отчёта внеси относительный путь к PDF и краткий результат проверки.

Если `md2pdf` или его зависимости недоступны, не устанавливай их без разрешения пользователя. Сохрани Markdown, явно укажи, что PDF не создан и почему, и не называй поставку полного отчёта завершённой.

## Stop conditions

Остановись и запроси решение пользователя, если:

- оба MCP недоступны или не возвращают реальные данные;
- название товара неоднозначно, а релевантный сегмент нельзя установить;
- требуется доступ к закрытой аналитике, которого нет;
- вывод зависит от метрики, которую нельзя получить;
- исследование выходит за согласованный регион, бюджет или ассортимент.
- для решения требуется национальная метрика Авито, но доступна только городская аналитика.

## Блокирующий quality gate

Перед выдачей любого результата проверь:

- [ ] есть раздел «Цель и условия исследования» и классификация канала в Stage 0;
- [ ] каждый недоступный или заблокированный источник обработан по `references/source-degradation.md`, а вывод не превышает допустимый уровень;
- [ ] не придуманы метрика, источник, регион, период или уровень данных; запрошенная география, покрытие каждого источника и режим географии записаны в разделе «Цель и условия исследования», паспорте и отчёте;
- [ ] данные `category`, `cluster` и `listing` не подменяют друг друга; контакты и просмотры не названы доказанным дефицитом;
- [ ] для веб-поиска в РФ использован Search API (Яндекс) либо это явно ограничено в матрице деградации; «Журнал поисковых запросов» сохраняет точные коммерческие/профессиональные фразы Wordstat до шаблонного расширения;
- [ ] для отложенного поиска явно сообщено пользователю об ожидании ≥5 минут и результат собран до истечения 12 часов;
- [ ] у каждого веб-факта есть URL, дата доступа и тип источника; защита не обходилась;
- [ ] каждый график создан из `charts-spec.json`, имеет источник, регион, период, уровень данных и `evidence_ref`; Wordstat и Авито не объединены на общей шкале;
- [ ] каждая страница PDF с графиком визуально проверена: подписи, легенды и шкалы не обрезаны, не выходят за край и не перекрывают данные; таблицы рядом с графиками распознаны как HTML-таблицы;
- [ ] общероссийский вывод подтверждён источником с покрытием РФ; городские данные Авито имеют названия городов и не агрегированы в Россию. При `national_with_city_sample` список и критерий городов указаны, а вывод ограничен «среди проверенных городов»;
- [ ] создан одноимённый PDF через `md2pdf`; в `_check.txt` все выбранные фразы имеют статус `True`, PDF и PNG-страницы ненулевые, а SVG-графики при наличии попали в PDF как векторные drawings;
- [ ] в отчёте есть проверяемые «Исходные данные», «История исследования», один следующий тест и ограниченный доступными данными статус `GO`, `TEST`, `HOLD` или `NO-GO`;
- [ ] SQLite содержит текущий запуск и новые наблюдения по фиксированной схеме либо в разделе «История исследования» указана точная ошибка и не сделан исторический вывод.
- [ ] создан паспорт запуска; для Авито задокументированы авторизация, точный ID локации и `evidence_ref` каждого использованного ответа.
- [ ] при доступных category-метриках Авито собрана только релевантная ветка категорий, а у каждого узла есть ID, родительский ID (если доступен), глубина, город, период и `evidence_ref`; несвязанные «все категории» не выданы за структуру товара.
- [ ] при двух и более сопоставимых category-строках в отчёте есть таблица «Предложение и отклик» и `market_profile` с раздельными панелями; при единственной строке объяснено отсутствие графика.
- [ ] проверены обязательные заголовки отчёта; недоступные источники отмечены в своих разделах, а не скрыты.

Для полного отчёта затем прочитай и выполни `references/extended-quality-gate.md`.
